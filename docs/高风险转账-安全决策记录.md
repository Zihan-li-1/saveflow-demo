## 3. 字段链追踪：验证码是否暴露给浏览器

追踪链路：`riskCheck()` → `Core.prepare()` → HTTP 响应 / Agent 响应 → 前端。

| 环节 | 位置 | 内容 | 是否含明文验证码 |
|---|---|---|---|
| 风险计算 | `core.mjs:139` `riskCheck()` | 返回 `{ riskLevel, requiredVerification: 'otp'/'none', warnings, ... }` | ❌ 无 |
| prepare 响应 | `core.mjs:291/318/353/400` | `risk: structuredClone(risk)` | ❌ 无（risk 对象本身无该字段） |
| 操作记录 | `core.mjs:446` | `record.verification = challenge.state`（仅 `codeHash` 与状态元数据，无明文码） | ❌ 只存哈希 |
| 发起挑战响应 | `core.mjs:445` | 返回 `challengeId / expiresAt / remainingAttempts / deliveryHint` | ❌ 无 |
| 校验响应 | `core.mjs:468` | 返回 `{ verified: true, operationId }` | ❌ 无 |
| 投递渠道 | `core.mjs` | `deliverVerificationCode(...)` 默认 **no-op**（不投递）；演示验证码固定为 `DEMO_OTP_CODE`，不在界面上明文展示（演示时口头告知） | ❌ 无（明文码不经服务端渠道/日志/界面） |
| 类型契约 | `contracts.ts:62` | `RiskResult` 无 `verificationCode` 字段 | ❌ 类型层面堵死 |
| HTTP 测试 | `banking-http.test.cjs:138` | 断言 `risk.verification_code === undefined` | 通过 |
| Agent 测试 | `banking-agent.test.mjs:64` | 断言 `risk.verificationCode === undefined` | 通过 |
| Core 测试 | `transfer-execute.test.mjs:51,54` | 断言 `risk.verificationCode === undefined` | 通过 |

**结论**：浏览器、HTTP 响应、Agent 响应、操作记录都拿不到明文码；明文码只通过 `deliverVerificationCode` 投递。

**⚠️ 需要注意的边界**：演示验证码固定为 `DEMO_OTP_CODE`（`src/lib/demo-otp.mjs`），不在界面上明文展示（演示时口头告知固定码），`deliverVerificationCode` 默认也不输出到服务端日志。这是「演示受控渠道」的有意选择（Mock 环境没有真实短信），但必须在文档与评审中**明确不称为真实短信 / 银行级 MFA**（见 §5）。

## 4. 已实现的安全保护

| 保护项 | 实现 | 测试 |
|---|---|---|
| 挑战绑定操作 | `challengeId = otp_<uuid>`，`record.verification` 挂在唯一操作上 | `verification.test.mjs` |
| 绑定预览哈希 | `startVerification/verifyVerification` 先 `verifyHash(record, previewHash)` | `verification.test.mjs:116` |
| 绑定有效期 | TTL 取 `min(2 分钟, 预览剩余有效期)` | `core.mjs:440` |
| 哈希存储 | `hashCode(challengeId, code)` SHA-256，仅存 `codeHash` | `verification.mjs:19` |
| 尝试次数限制 | `VERIFICATION_MAX_ATTEMPTS = 3`，错满锁定 | `verification.mjs:50-58` |
| 速率限制（单操作） | 相邻两次发码间隔 `VERIFICATION_ISSUE_COOLDOWN_MS`(30s)，冷却期内重发抛 `VERIFICATION_RATE_LIMITED` | 验收 `[P1 步骤5]` |
| 速率限制（按用户窗口） | 每个 Core 实例在 `VERIFICATION_ISSUE_WINDOW_MS`(60s) 内最多发码 `VERIFICATION_ISSUE_MAX_PER_WINDOW`(5) 次，**新建操作也无法重置发码额度** | `core.mjs` `otpIssueLog` |
| 并发尝试计数 | `store.mutateVerification` 行锁（Postgres `FOR UPDATE`）内基于新鲜记录原子消费一次尝试，避免并发校验错误码丢失 `attempts` | `verification.test.mjs` / `transfer-execute-acceptance.test.mjs` |
| 单次有效 | `verified` 后再用 → `VERIFICATION_ALREADY_USED` | `verification.test.mjs:89` |
| 重发作废旧码 | 重新 `startVerification` 覆盖 `record.verification` | `verification.test.mjs:100` |
| 恒定时间比较 | `timingSafeEqual` | `verification.mjs:36` |
| 执行前状态核验 | `execute()` 检查 `verification.status === 'verified'` | `core.mjs:485` |
| 执行幂等 | 同一 `operationId+previewHash` 重复 execute 返回同一回执 | 验收 9/12 |
| 输入白名单 | `validateTransfer` 拒绝未注册字段（含 `skipVerification` 等） | 验收 11/12 |

## 5. 演示投递声明

- 演示验证码固定为 `DEMO_OTP_CODE`（`src/lib/demo-otp.mjs`，默认 `123456`），**不在界面上明文展示**（演示时口头告知固定码）；`deliverVerificationCode` 默认 no-op，**明文码不写进界面、服务端日志或任何响应**。
- `SAVEFLOW_DEMO_OTP_CODE` 环境变量可覆盖演示固定码（覆盖后需同步口头告知的固定码）。
- **固定码仅限定在合成演示环境**（`getConfiguredBankingCore`）：本地临时演示（无 `DATABASE_URL` 且非 Netlify）默认允许；任何持久化 / Netlify / 类生产配置必须显式 `SAVEFLOW_DEMO_OTP_ENABLED=true` 才允许，否则不注入固定码 → OTP 用随机码且无投递渠道 → 校验不可能成功 → **执行能力保持关闭（安全失败）**。
- **本地 Core 库演示已显式开启固定码**（2026-10-28）：`compose.postgres.yaml` 的 `web` 服务设置 `SAVEFLOW_DEMO_OTP_ENABLED=true`、`SAVEFLOW_DEMO_OTP_CODE=123456`，使持久化（Postgres）链路下演示也能用固定码 `123456` 通过校验（口头告知、界面不展示）。**部署到真实/类生产环境前必须移除或置 `false`。**
- **本实现不声称是真实短信、真实银行级 MFA**。若将来接真实渠道，应注入 `options.deliverVerificationCode` 为短信/邮件/推送，并移除固定演示码逻辑。

## 6. 已知缺口与风险

1. ~~速率限制缺失~~ **已解决**：`startVerification` 现于相邻两次发码之间加 `VERIFICATION_ISSUE_COOLDOWN_MS`(30s) 冷却期，并叠加按用户窗口限制（60s 内最多 5 次），冷却/超窗均抛 `VERIFICATION_RATE_LIMITED`，堵住「重发→试 3 次→重发」与「新建操作→无限重置发码额度」的暴力枚举（见 §4、验收 `[P1 步骤5]`）。
2. **执行桥与 OTP 的耦合**：`core.mjs` 同时含通用 OTP 方法（`startVerification/verifyVerification`）与桥专用胶水（`executeTrial/trialAuthorized/startTrialVerification/verifyTrialVerification`），文件层面无法干净切分；已随主线合入，若需再拆需另起审查。
3. ~~明文码在服务端日志~~ **已解决**：`deliverVerificationCode` 默认改为 no-op，明文码也不在界面上展示（演示时口头告知固定码），不再进入界面、服务端日志或任何响应（见 §3/§5）。
4. ~~并发校验丢失尝试次数~~ **已解决**：`verifyVerification` 改为经 `store.mutateVerification` 在行锁内基于新鲜记录原子消费一次尝试，Postgres 多实例并发校验错误码不再丢失 `attempts` 计数（见 §4）。
