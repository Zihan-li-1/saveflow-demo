# 储蓄目标规划与卡片设计（待审核）

日期：2026-10-22。基线：`main` 提交 `7127eab8896d5c4e5aabfbde51d689c2e5ca0cf7`。

## 目标和边界

用户说“年底存够 1 万元，推荐一份计划”时，系统先得到可核算的储蓄计划，才显示计划卡片。卡片用中文步骤名称，不显示 `bill.analyze` 等内部 action 编号。模型根据已有分类流水和用户补充的近期数据分析消费习惯、提出各类别月度建议；程序负责金额、时间、数据来源和输出合同的复核。沿用 `orchestrator.goal`，不新建储蓄 Skill。此计划只读，不创建转账、理财申购或消费规则。购物联动不属于本次改动。

## 已知现状

`handleGoal` 已读取账户、订阅、卡片、产品，并把 `amount`、`deadline` 原样存入 `goal_plan`，但未计算储蓄缺口或调用理财筛选。`BankingReadCards.tsx` 把 `step.action` 直接渲染成标题。Mock 流水只有 2026-06 至 2026-08，数据快照是 2026-09-01；用户在 2026-10-22 询问年底计划时，不能把这些流水称为当月现状。现有 `getSavingGoal()` 是另一个目标，不能作为新目标的已存金额。

## 方案选择

1. 纯规则预算：数字可靠，但难以按消费模式解释类别建议。
2. 模型直接输出整份计划：表达灵活，但金额、日期和引用可能不一致。
3. **采用混合方案**：服务端算目标数学与核查模型建议；模型只输出有证据的习惯观察、分类建议和理由。用户已认可该方案，并选择“先补齐近期数据再出卡片”。

## 输入与数据流

1. 现有 Intent Parser 仍只抽取 `orchestrator.goal` 的目标文本、目标金额与截止日期。金额或日期不明确时先追问，不由模型猜。
2. 目标规划入口检查是否有本目标的已存金额，以及**最近一个完整日历月**的收入和分类支出。缺失时只返回 `needs_plan_inputs`，页面展示补充表单；不输出计划卡片。第一版由用户按消费类别填写最近完整月数据。原有 6–8 月 Mock 只作已注明日期的历史参照，不能填补缺失的近期数据。新目标不能套用旧目标余额。
3. 表单包含 `saved_amount_minor`、`month`、`income_minor`、按仓库现有类别填写的非负整数分支出；总支出由服务端求和，表单可显示这个合计。保存于本轮会话带完整性保护的续接状态，标注 `user_provided`，不写共享 Mock JSON；完整性保护不代表财务数字已核实。若已有可信 Repository 的该月数据，优先从 Repository 读取并标注来源；不得静默混合相同月份的两种来源。
4. 服务端将来源、快照时间、收入、分类支出与目标数学组成最小化上下文，调用独立于 Intent Parser 的模型建议步骤。仅传分类汇总，不传卡号、原始商户或访问凭据。模型输出固定 JSON：`observations`（类别、比较依据、结论及不确定性）、`category_budgets`（类别、建议月上限整数分、理由、证据引用）、`caveats`，以及 `self_review`（是否逐项检查了数据覆盖、类别引用、固定开销、建议合计和不确定性，并列出未通过项）。模型不输出最终应存金额或可行性结论；这些由服务端计算。
5. 模型必须先完成 `self_review`，未通过就不能生成卡片；但自检只是模型声明，不是可信复核。服务端仍须独立重新计算并验证输入、证据和建议，随后组装 `goal_plan`；客户端仅在状态为 `verified` 时渲染计划卡片。生成失败或复核失败时返回可理解的错误/澄清，不把未复核 JSON 当作建议展示。允许一次受限重试，不能在重试后放松校验。

## 可核算规则

- 以服务端当前 `Asia/Shanghai` 日期为准。月度储蓄从**下一个完整月的月初**开始计，截止日当天或之前的月初为一次储蓄机会。例如 2026-10-22 至 2026-12-31 为 2026-11-01、2026-12-01 两次；不足一次时只提示期限过短，不编造“每月计划”。卡片写明这个口径。
- `remaining_minor = max(0, target_amount_minor - saved_amount_minor)`；`required_monthly_minor = ceil(remaining_minor / opportunity_count)`。已存金额是用户对**这个目标**的声明，必须标注为用户提供，不能把账户总余额当已存目标金额。
- `expense_minor = sum(category_amount_minor)`；`observed_surplus_minor = income_minor - expense_minor`；`monthly_gap_minor = max(0, required_monthly_minor - observed_surplus_minor)`。收入、支出和预算一律整数分，不使用浮点金额。
- 规划预算的每一个类别必须来自可用类别表，且每类恰好一次。模型不得改写用户提供的已发生金额。建议总消费加每月必需储蓄超过最近月收入时，卡片标为“存在缺口”，不得宣称可行；建议类别之和必须等于卡片展示的建议消费总额。房租、通信等固定开销默认不得下调；只有用户明确提供变化且能核实来源时才允许重算。订阅标记“可能闲置”不等于已取消或已节省。
- 若近期数据来自用户填写，复核只证明**算术与引用一致**，不证明用户输入的真实性或未来收入稳定。卡片用“按所填最近月数据测算”，不能写“已核实真实账单”。历史样本有限或趋势互相矛盾时，模型必须写“可能”并显示低置信度，不能宣称稳定消费习惯。
- 模型引用的类别、月份及变化必须能从输入汇总重新算出；不存在的类别、商户、账单或未经确认的固定开销变化一律拒绝。限制输出长度，拒绝未知字段、注入式指令和收益承诺。

## 卡片 UI

顶部：`储蓄计划草案 · 已完成算术复核`，目标 ¥X、已存 ¥Y、截止日期、数据月份与来源。主区域按顺序显示：① 还差多少、剩余多少次完整月、每月最低需存；② 最近月收入／支出／结余以及与目标的月度差额；③ 每个消费类别的“最近月实际—建议月上限—建议理由”，理由附观察证据与不确定性；④ 可行性提示、数据假设和下一步。类别图形可用现有卡片样式的条形对比，手机上改为纵向列表。`bill.analyze`、`subscription.list`、`card.get`、`wealth.recommend` 在所有用户可见的步骤标题中分别显示“分析收支”“查看订阅”“查看卡片预算”“筛选理财产品”，内部 action 不变。

在补齐输入前只显示“补充近期数据”卡：目标金额/日期、目标已存金额、最近完整月、收入和分类支出、数据来源提示。不得显示空计划。若数字不满足目标，展示差额与可调整的期限/目标建议，不以模型文案掩盖缺口。旧的 `PlanCard` 与 `create-plan` 是另一条演示流程，不自动写入；若未来要从此卡创建目标，须单独对齐其月度上限和确认合同。

## 理财触发边界

储蓄卡片完成复核后，只有用户明确要求产品推荐或主动点击“查看理财产品筛选”，并补齐风险承受、期限和流动性条件，才单独调用现有只读 `wealth.recommend`。储蓄金额和应急资金不自动挪作可投资余额；不能依据收益率反推“保证存够目标”。缺少适当性信息时只展示澄清/风险测评入口。任何申购仍走独立 L3 预览和确认。

## 失败与验收

缺近期数据、目标已存金额、目标金额或日期时绝不出计划卡；过期日期、零储蓄机会、不完整分类、负数、非整数分、模型引用不存在、建议类别总和与显示总额不一致、固定开销无依据下降时拒绝。收入不足属于已复核的“存在缺口”结果，不是假装可行，也不靠伪造预算使总额凑平。模型超时或格式错时只显示可重试状态，不显示未经复核的计划。验收用 2026-10-22 至 2026-12-31 的 1 万元目标验证两次月初机会和每月 5000 元（已存为 0 的前提）；同时覆盖已存部分金额、已达目标、跨年、月中截止、收入不足、模型故意造数、用户输入与旧 Mock 冲突，以及中文动作标题。端到端验证从自然语言输入、补充表单、模型响应、服务端复核到卡片，不以单元测试代替页面检查。
