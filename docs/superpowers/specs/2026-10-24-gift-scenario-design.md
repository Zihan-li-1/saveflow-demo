# 鲜花与蛋糕跨场景预约：设计审核稿

日期：2026-10-24。用户已通过本设计，实施记录更新于 2026-10-26。此文件描述目标，不能替代运行验证；当前验收证据见 `docs/Gift-Purchase-Verification.md`。

配套文件：[逐动作输入、输出、错误码及 Mock 数据契约](../../Gift-Purchase-Actions.md)。本设计说明用户流程；契约规定调用边界。

## 1. 用户已决定的事项与完整目标

用户提出“这个月预留 1000 元活期，在某一天订花和蛋糕”，系统要识别一个跨场景目标，调用需要的 Skill，最终通过平台接口完成经用户确认的订单，而不是只列出建议步骤。

已确认：

- 1000 元是应用内预算预留，账户余额不动，提醒不要挪用；不是银行冻结、扣款或理财申购。
- 两个选品入口都保留：问答收集偏好、LLM 辅助搭配；按类别给商品链接让用户挑选和反复换一批。
- 用户确认具体商品、总价和配送信息后，Agent 才调用下单接口。提前批准一个预算，不等于批准未来未知订单。
- 团队暂时没有购物平台的商户/开发者权限，未来可能取得。

完整完成条件仍包含真实平台适配和验证。目前先开发可运行的模拟购物服务并经 HTTP 调用它；真实商品目录、真实链接、真实下单和平台回调是待外部权限就绪后的交付门槛。模拟通过不能证明这些门槛已完成。

本次实跑 Scenario 与 Commerce 相关测试：13 项全部通过。这些测试覆盖现有只读规则、Mock 规划和幂等约束，没有覆盖生日购物端到端能力。

选择方案：用户已选“确认具体订单后调用接口”。只给链接无法满足代下单目标；先授权预算再无人确认购物未获选择。技术上使用一个明确的 Scenario 编排流程和独立 Commerce 服务，不新增多 Agent 框架。复用现有 Qwen 网关、实体解析、确认/错误处理习惯与 PostgreSQL 技术栈。

保留原 `scenario.create_rule` 的只读语义。新注册 `scenario.plan_purchase`，将“预算 + 日期 + 花与蛋糕”识别为一个有约束的复合业务意图；其他无关的多指令仍按原规则澄清。新增 action 必须同步原始契约、解析器、运行时校验和路由，不能只改提示词。

## 3. 用户能看到的流程

1. 识别金额、预算月份、用途与日期。若只说“某天”，追问具体年月日和时间；若不明确，追问是那天才下单还是那天送达。按会话时区解析，保存用户原话与确定日期。
2. 显示“预留 1000 元购物预算，银行余额不变”的计划预览。用户确认后保存预算标记和预约；独立记录尚未选定的商品。预算不足时给出缺口，不声称已预留成功。
3. 两个按钮：“问我几个问题，帮我搭配”“给我商品链接，我自己选”。后续可切换，保留已确认偏好与已选商品。
4. 选好花和蛋糕后，从可信表单选择/填写收件人、电话、地址和送达时间；完整地址不发送给 LLM，只给它完成推荐所需的配送区域。
5. 重新查询两件商品的价格、规格、库存、配送时间、运费与取消条款。展示完整订单预览，以及预算剩余金额。费用合计不能超过 1000 元。
6. 用户核对后分别确认具体商户订单，或者一次确认预览中明确列出的两个订单（仅限两个均已准备、且清楚列出逐单金额/信息的情况）；执行器按独立订单处理，绝不声称跨商户原子成功。实现首版采用逐单确认，减少误解。
7. 返回每笔订单真实状态：已创建待支付、商家已接单、失败、结果待核实、已取消等。无支付授权/接口则给平台支付入口；“已创建”不显示成“已付款/已送达”。

问答选品至少覆盖：送礼对象/场合（可跳过）、花材/颜色/香味禁忌、蛋糕人数/尺寸/口味/过敏原限制、预算是否含配送费、可配送区域、日期和时间窗。只问会改变选择的缺失项；默认总预算含商品、包装、配送及平台费用，价格未确认时明确标记待报价。

分类链接模式可用“简约花束、生日花束、低香花束”“水果蛋糕、巧克力蛋糕”等目录标签；真实候选由平台或审核后的目录提供。每张卡片显示商品名、价格/运费状态、规格、商户、送达信息、推荐依据、来源与更新时间。支持换一批、修改偏好、仅换鲜花或蛋糕、去重与分页。缺失过敏原信息不可标记“安全”。

链接来自服务端审核的平台域名和返回的商品记录。LLM 不能生成 URL、价格或库存。打开链接仅视为查看，不能当作选中或已下单。用户返回后点选明确商品/SKU；粘贴其他链接需通过已支持的平台解析，否则提示暂不支持。开发目录链接指向明确标注“模拟商品”的详情页，不能伪装真实商家链接。

## 4. LLM 和各 Skill 的职责

`用户需求 → A 的 ParsedIntentEnvelope → 服务端解析/校验 → Scenario Purchase 编排 → Bill/财务查询 + 预算标记 + Commerce → 确认适配器 → 平台订单接口 → 逐单回执`

- **LLM**：提取偏好、发现歧义、组织追问、解释候选搭配。每个提取值保留来源；用户纠正覆盖旧值。它只从可信商品候选中选择编号并解释，结果再经过规格、预算、配送和禁忌的确定性过滤。
- **A / 意图层**：新增 `scenario.plan_purchase`，只输出原始引用与业务槽位；不输出商户令牌、服务端 ID、confirmed、执行工具名或成功状态。
- **Scenario（E）**：维护会话、模式切换、预算用途、日期、选品、订单前置条件与整体进度，调用所需 Skill。其内部流程节点由服务端固定定义，不执行模型自创步骤。
- **Bill/财务查询**：查询现金流与近期义务，提供来源和时间。数据不完整时先补齐；不能把信用卡消费额度当活期余额。
- **预算 Store**：保存逻辑预留与用途，不改银行账务。个人账户余额与应用内建议可支配金额分别展示。查询可支配金额时扣除其他有效预算，不重复扣本流程预算。
- **Commerce（独立模块）**：商品搜索、报价、订单预览、执行和状态查询；真实平台适配留在服务端。Wealth 不负责购买商品，这个活期购物例子也不会自动触发理财申购或赎回。
- **B / 风险与执行模式**：复用精确预览、幂等、确认失效、结果不确定的约束。预算标记与购物订单使用新的业务 Store，不为它们改写已有资金 Action；未来若涉及赎回，单独走 B 的现有确认链路。

当前代码实际使用 `src/agent/parsed-intent.ts` 中的 `schemaVersion/action/slots` 单意图合同，而团队总体文档称为 `ParsedIntentEnvelope`。实施时在 A 的服务端适配层对齐，不能凭空假定已有完整 Envelope 运行时。默认 TrueForge 网关还附加“多个动作或先后依赖必须返回 clarify”的约束，因此需同时更新 `server/trueforge-banking-runtime.mjs` 与共享解析提示：允许已注册的生日购物复合业务意图，仍禁止模型输出任意执行计划。

当前 HTTP 入口以演示访问码鉴权，已有 Scenario scope 部分依赖 IP，不能当作真实客户身份。新的模拟流程使用服务端签发的持久会话凭据绑定 owner 与流程，所有读写和确认均校验归属，不接受请求体任意 owner、不用 IP 识别人。真实平台上线门槛还包括稳定的已认证用户身份、该用户的平台授权和安全地址存储；共享演示访问码不得直接启用真实购买。地址/电话和确认凭据均不写入 LLM 上下文或普通日志。

## 5. 拟新增动作契约

所有输入均拒绝未知字段。对外使用 snake_case 和 `{amount_minor,currency}`（整数分 CNY），内部适配沿用项目 camelCase。服务端 IDs 来自可访问对象解析和可信引用，不接受模型编造。

| 动作/接口 | 输入要点 | 输出 | 写入/授权 |
|---|---|---|---|
| `scenario.plan_purchase`（A 注册） | `budget`、`budget_month`、`date_expression`、`date_meaning`、`items`、可选偏好/选品模式 | 缺失槽位或流程草案 | 仅草案；不自动保存预算、调度或订单 |
| `scenario.purchase.save`（可信 UI） | draft_ref、expected_version、plan_preview_ref、plan_confirmation_token | 预算预留及预约回执 | 明确确认；同事务写预算和预约 |
| `scenario.purchase.update`（可信 UI/经过校验的对话） | workflow_ref、expected_version、白名单变更 | 新流程版本/缺失项 | 改商品、日期或地址使旧订单预览失效；金额/预约变更另行确认 |
| `commerce.search`（内部调用） | category、已确认偏好、区域、送达时间、预算约束、cursor | 来源可核对的候选及链接 | 只读 |
| `commerce.quote`（内部调用） | 解析后的商品/SKU、数量、address_ref、时间窗 | quote_ref、价格分项、库存、有效期、取消条款 | 只读，不承诺已占库存 |
| `commerce.order.prepare` | workflow_ref、expected_version、单份 quote_ref；商品/SKU/数量读取已绑定报价 | 逐单精确预览、hash、期限、付款能力 | 不下单 |
| `commerce.order.execute`（可信 UI） | operation_ref、preview_hash、单次确认凭据 | 订单回执或 unknown | 具体确认后调用平台；不能从聊天词“确认”直接越过 UI |
| `commerce.order.status` | operation_ref | 当前平台状态/证据 | 只读，处理 unknown 首选此接口 |
| `scenario.purchase.cancel`（可信 UI） | workflow_ref、expected_version、确认 | 取消计划/释放未占用预留的回执 | 不把取消计划等同取消已创建外部订单；已存在的订单列出需处理事项 |

模型不能调用上述内部 execute 接口。第一版不提供任意工具名透传。现有 suggest_only 契约继续拒绝写步骤。

标准输出保留 `as_of`、`context_snapshot_id`、`evidence`，并有 `execution_environment=mock|live`。模拟数据必须 `synthetic_demo_only=true`。缺少偏好先返回 `needs_clarification`；错误码至少包含 `DATE_AMBIGUOUS`、`BUDGET_EXCEEDED`、`INSUFFICIENT_PLANNING_BALANCE`、`PRODUCT_UNAVAILABLE`、`DELIVERY_UNAVAILABLE`、`PLATFORM_NOT_CONNECTED`、`QUOTE_EXPIRED`、`PREVIEW_STALE`、`CONFIRMATION_REQUIRED`、`ORDER_STATUS_UNKNOWN`、`IDEMPOTENCY_CONFLICT`。逐动作错误码见配套草案，错误必须携带可恢复的下一步。

## 6. 预约、预算和异常恢复

“届时下单”：到期任务只刷新条件、准备报价并生成应用内待确认事项。必须用户当时确认具体预览；不继承数周前的预算确认。到截止时间无人确认，标记错过窗口，不偷偷补单。

“届时送达”：优先使用平台支持的预约配送，在当前有效报价下由用户确认并创建预约订单。平台不支持指定日期时，显示能力缺口，不能宣称保证送达。

预算表保存总预留、尚可分配金额、已占用订单金额、已确认消费与释放金额。总额始终可对账：`总预留 = 未分配 + 订单占用 + 已消费 + 已释放`。订单 unknown/待支付时保持占用，避免再次花掉同一预算；确认失败/取消后才能释放该单占用，退款申请中不能算退款到账。已有交易入账与订单消费通过关联引用去重，避免从可支配资金重复扣减。

使用已有 PostgreSQL 技术栈存流程、预算、订单操作、调度任务和事件去重；按 owner 和流程版本隔离。到期 worker 使用可信时间、租约领取和唯一触发 ID，重启后可恢复。同一订单幂等键重放返回原结果；同键不同内容冲突。先落库 executing，再请求平台；超时保留 unknown，使用平台订单键查询，不换新键自动重下。

若平台不支持幂等/商户订单号查询，则不开放自动执行能力，保留链接/人工核验路径。一单成功另一单失败时展示逐单状态，用户决定更换商品或取消；不宣称成功单已回滚，不自动接受替代品或加价。预算不足且已存在不确定订单时先查单，不能绕过。

后台调度复用可部署的服务端 worker，网页关闭仍可执行；开发提供人工推进时钟的验收入口。未配置持久化数据库或 worker 的环境必须显示“未启用后台预约”，不能仅靠浏览器定时器宣称任务已安排。产品提醒先使用应用内待办，不新增真实短信/邮件发送。

## 7. 模拟服务和真实平台接口

模拟服务要是独立 HTTP 能力，包含商品目录、区域库存、版本化报价、订单创建、查单、预约和状态事件；不能直接由测试伪造一张成功回执。至少有多个花材、蛋糕规格、两家商户、超预算和不配送候选。控制开关支持价格变化、缺货、先受理后超时、重复回调、部分成功与待支付，服务端日志与数据库回执可交叉核对。

实际平台选定后才实现该平台的凭据、签名、授权刷新和回调验证；密钥只在服务端配置。适配器报告明确的 capabilities（搜索、报价、预约、下单、支付、查单、取消等），未支持的能力拒绝调用，不把任意平台 URL 当可执行工具。

官方接口调查示例：抖音生活服务的 `plugin.createOrder` 需相应行业插件权限，并在创建订单后调起小程序收银台；其运行在平台小程序环境，不能直接当本项目通用 Node 下单接口。它说明“建单、支付、预约”须按平台分别适配，不代表本项目已选择或支持抖音。

## 8. 验收与交付

1. 一句话生日购物需求正确路由 Scenario，调用所需查询与 Commerce，UI 不直接显示内部 action 列表代替完成结果。
2. 预算确认后银行余额完全不变；预算可查看、修改、取消，多个预算不会超分配。
3. 问答真实调用现有 LLM 网关并做槽位校验；含糊、矛盾或注入文本不能绕过确认。离线模式清楚标识规则模拟。
4. 链接模式提供来源可验证的候选，能连续换一批、保留选择、切换问答；真实与模拟链接明确区分。
5. 明确下单时间/送达时间、年月日与时区；跨月预留到结束/取消前仍有效，不能月底无声释放。
6. 没有最终确认、报价过期、预算/地址/规格/配送时段变化时，平台请求计数保持 0。
7. 用户精确确认后，模拟服务收到真实 HTTP 下单调用并返回可查询的独立订单，状态与账本一致；支付与履约分阶段展示。
8. 并发、重启和重复事件不重复建单/分配预算；超时查单可以恢复原订单，不能重复执行。
9. 两商户部分失败、用户修改/取消、订单未知、退款处理中均保留真实状态与预算占用。
10. 未配置平台/数据库/worker 时返回明确能力状态；真实平台验收必须有实际授权环境、可验证订单回执、真实链接和状态查询证据，不能由 Mock 测试替代。

团队交付按顺序：动作契约与 Schema → Scenario/Commerce/预算与调度实现 → 两种 UI → Mock HTTP 集成与端到端测试 → PR。共享 A 层变更明确列在 PR；不修改共享财务种子，不混入 PR27。个人教学稿单独保存，解释 LLM 与规则、幂等/回执、预算与银行冻结差异，以及如何自行审核。

## 9. 已审核的实施约束与外部条件

已审核流程包含“预约到期后需用户再次核对具体订单”“逐商户确认”“商品链接模式可切换到接口下单”。这些约束不授予无限期自动付款权限。

未完成的外部条件：真实平台权限、具体供应商与真实订单/支付能力；部署用持久化数据库及后台调度配置。在这些条件就绪前，完整目标保持未完成，不以模拟验收替代真实集成。

设计独立审阅结果：未发现需要再向用户追问的实质性规划缺口；真实平台与部署条件已作为后续交付门槛记录。用户已通过设计，当前实现与未完成验收项另记，不以通过设计代表通过产品验收。
