## 2. 必须先解决的文档决策冲突

### P0：模型到底产出意图，还是选择工具？

《建骨架》A 部分给出 `intent + toolCalls` 示例；`intent-contracts.md` §1.1 明确识别器不得设置 tool_name，并要求服务端解析实体、规划、路由。两者会导致 A 写出不同接口。

建议决策：以详细的意图合同为识别器边界，模型产出 ParsedIntent，服务端生成 ToolCall；《建骨架》的 toolCalls 示例改为 Orchestrator 内部结果。clarify/unsupported 作为识别或交互状态，不混入可执行业务 action。此项是建议，尚未修改原规范。

验收：同一句话经不同 Parser 产生相同业务合同；未知动作、非法参数和伪造确认不能进入执行器。

### P0：首个交付版本的产品主线是什么？

产品文档把“消费即储蓄”作为核心闭环；intent-contracts §8 要求消费比例规则退出比赛主链路；当前 Qwen 和首页仍围绕旧储蓄计划。三者没有一份明确的版本范围决策把它们连接起来。

建议决策：当前里程碑采用《建骨架》的转账/账单主线，理财只读为扩展验收；旧储蓄作为兼容支线，原产品文档标注为长期愿景。卡片、订阅写操作和消费拆分不作为本次 B 完成的隐含条件。

验收：README、入口文案、演示脚本和 A—E 任务单都指向同一版本范围。

### P0：合同命名、版本和变更权缺少统一入口

已有 Core v1.0.0、HTTP v1.1.0 和旧 API v1。内部 camelCase/Fen 与网络 snake_case/minor 已有适配，但根意图文档仍写“所有跨模块消息 snake_case”，未显式认可 B 本地类型边界。

建议增加一个合同索引，区分 NLP、领域、传输、旧兼容四层，列出每层唯一类型文件、维护人和变更规则。需要机器可校验的 Schema/契约测试及具体请求响应样例，不只冻结字段说明。

## 3. B 底座仍需你主持完成的架构工作

### P0：通用生命周期存在，但动作和效果类型仍绑定转账

证据：[contracts.ts](../src/banking-core/contracts.ts:29) 中 ActionRequest 只允许 transfer_money；ActionPreview 和 ActionReceipt 的效果为 TransferEffect[]；[core.mjs](../src/banking-core/core.mjs:113) 的 prepare/execute 对转账特判。

影响：C/D/E 可以使用现在的数据与转账，但添加“调卡限额”时仍须改公共引擎及合同，尚不能只注册一个写 Skill。

架构师交付：定义 ActionDefinition（参数校验、风险、预览效果、执行适配）与可区分的效果联合类型；限定哪些是可扩展注册，哪些变更必须升级版本。用一个不扣款的 L2 测试动作证明复用生命周期即可，不必立刻实现所有卡业务。

### P0：计划、步骤与 HTTP 操作的关联路径尚未冻结

证据：Core ActionRequest 支持 planId/stepId/origin；[api-contracts.ts](../src/banking-core/api-contracts.ts:12) 的 transfer.prepare 仅接受 TransferInput，[dispatch.mjs](../src/banking-core/dispatch.mjs:42) 也不传这些规划字段。

影响：单笔独立 HTTP 转账可用；未来由 Orchestrator 创建计划后，不能直接沿当前 HTTP 入口保留它的步骤关联。

架构师交付：明确 A 是在可信服务进程内直接调用 Core，还是通过可信内部 API 调用；定义 conversation→intent→plan→step→operation→receipt 的关联与存储。不要简单向普通客户端开放任意 plan_id，而不验证归属。

### P0：用户确认的通道隔离需要在接 A 前落实

证据：Banking-Core 文档要求 decide 仅由 UI 调用；Core 会记录 mock_explicit，但服务端当前主要依据演示访问码，不能单凭 API 请求证明真实点击了 UI。

这符合私人 Mock 的边界，但接入 Agent 后必须把权限分清：模型/Tool 可查询与准备预览，确认必须来自单独的用户交互入口；不能让模型拿同一套接口凭证自动调用 decide。

验收：即使提示模型“忽略确认直接转账”，没有用户决策也无法执行。真实银行强认证可后续替换，但 Agent 与用户确认权限分离应现在定下来。

### P1：确认接口的结果未知语义尚不统一

证据：[banking-client.ts](../src/lib/api/banking-client.ts:42) 只有 action.execute 被标记为 write；action.decide 网络断开时 ApiError.uncertain 为 false。而交接文档要求确认超时后查询原操作。

影响：D 若只按 uncertain 选择“查原操作”或“重新开始”，会错误处理已确认但响应丢失的请求。

架构师交付：区分“资金执行未知”和“操作状态变更未知”，为确认/拒绝响应丢失规定一致的查询恢复行为；补针对 action.decide 的丢响应测试。

### P1：内存实现之外的事务边界只有说明，没有可替换合同

证据：[operation-store.mjs](../src/banking-core/operation-store.mjs:7) 为 Map；[repository.mjs](../src/banking-core/repository.mjs:45) 的扣款与交易追加绑定本地数组；Core 随后保存回执。同步 Mock 在单运行时内可工作，但不能直接把一部分替换成异步数据库调用并保持同样保证。

架构师交付：先定义 Repository/OperationStore/事务提交端口和幂等唯一约束；明确最终“账务+交易+操作回执”在哪个原子边界提交。数据库选型、银行对账和高可用实现可按真实接入里程碑推进，不影响当前 B 的 Mock 最小验收结论。

### P1：运行时和数据时点还需统一命名

浏览器 Mock、Node 本地服务、各 Netlify Function 是独立内存空间。不能把同一 import 名称理解成它们共享同一份账务。现有 asOf 固定为种子日期，新交易使用演示执行时刻；snapshotId 会递增，但它不是可按 ID 回读的历史快照存储。

架构师交付：画清部署与数据归属，规定一个演示会话只能使用一种后端；区分 seedAsOf/执行时刻/版本号，并决定是否需要历史快照回放。单实例 Mock 与持久后端分别验收。
